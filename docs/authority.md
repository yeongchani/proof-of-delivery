# 권한과 지급 운영

[README](../README.md)

새 구현은 `AuthorityEscrow`이며 기존 `MilestoneEscrow`와 ABI·서명 형식이 다릅니다. 두 계약 모두 공개 테스트넷 배포를 완료했다고 주장하지 않습니다. 기존 [테스트넷 안내](testnet.md)는 v1 전용입니다.

## 누가 무엇을 결정하나

| 주체                       | 권한                                                     |
| -------------------------- | -------------------------------------------------------- |
| 발주자                     | 고정 조건 제안, 대금 예치, 이의 신청                     |
| 개발자                     | 조건 승인, 이행 보증금 예치, 소스 키 공개                |
| 양측 공동                  | 검증자 교체 승인                                         |
| 양측 각각                  | 결과 제출 전 검증 권한 정지                              |
| 등록 검증자                | 고정 정책과 기준에 대한 결과 서명. 금액·수령인 변경 불가 |
| 계약 배포 때 지정한 중재자 | 이의 사건의 승패 판정. 주소는 불변                       |
| 누구나                     | 조건이 도래한 지급·보관금 지급·기한 환불 호출            |

검증자 교체는 같은 주소·다음 권한 버전에 대한 양측 승인 후 적용합니다. 회수·교체 때마다 버전이 바뀌어 과거 서명은 무효가 됩니다. 통과 결과가 접수된 뒤에는 권한 변경을 동결하고 이의 절차로 처리합니다.

금액·기간·기준·러너 지문·AI 정책은 계약에서 바꾸지 않습니다. 변경 요청은 새 계약을 제안해 기록할 수 있지만 진행 중인 계약을 자동으로 대체하거나 자금을 옮기지는 않습니다. 전용 변경요청 관리 화면은 없습니다.

## 시간과 자금

납품 기한은 개발자의 조건 승인 시 시작됩니다. 대금·보증금이 일부만 예치되어도 기한이 지나면 환불할 수 있습니다. 양측 예치가 완료돼야 결과를 접수합니다.

- 정상 지급: 대금에서 보관금을 뺀 금액과 개발자 보증금 반환. 보관금은 지급 시점부터 합의한 기간 후 개발자에게 지급합니다.
- 개발자 중재 승: 위 정상 지급에 고객의 이의 보증금을 더합니다.
- 고객 중재 승: 대금과 양측 보증금을 고객에게 지급합니다.
- 검증·중재 시간 초과: 대금과 고객 이의 보증금은 고객에게, 개발자 보증금은 개발자에게 반환합니다. 무응답을 곧바로 어느 한쪽의 과실로 간주하지 않습니다.

권한 정지를 악용한 지급 방해 가능성, 중재자의 편향, 실제 납품에 대한 보상 문제는 남아 있습니다. 코드가 계약상 자금 처리 규칙을 집행한다는 사실과 경제적으로 공정하다는 주장은 다릅니다.

## 지급 호출 프로그램

`keeper`는 명시한 계약 번호만 한 번 확인합니다. 상시 스케줄러를 설치하지 않습니다. 기본값은 조회·시뮬레이션이며 `--send`를 지정할 때만 거래를 보냅니다.

```powershell
npm run build
$env:RPC_URL = '<사용할 RPC>'
$env:CHAIN_ID = '<동일 체인의 ID>'
$env:AUTHORITY_ESCROW_ADDRESS = '<새 AuthorityEscrow 주소>'
npm run keeper -- 1 2
# 가스 비용을 낼 KEEPER_PRIVATE_KEY를 별도 주입한 후에만:
npm run keeper -- 1 2 --send
```

호출자는 지급 대상과 금액을 선택할 수 없습니다. 다른 호출자가 먼저 실행하면 거래가 실패할 수 있으며 무한 재시도하지 않습니다. 상시 호출·가스 잔액·실패 알림 운영은 배포 단계의 과제입니다.

## 증거의 의미

GitHub CI는 `authority-demo-evidence` artifact를 30일 보관합니다. main push에서 테스트가 통과하면 별도 작업이 `authority-demo.json`에 GitHub 출처 증명을 붙입니다. 출처 증명 권한이 있는 작업은 저장소 코드를 checkout하거나 실행하지 않습니다.

다운로드한 파일은 다음 명령으로 확인할 수 있습니다.

```bash
gh attestation verify authority-demo.json -R yeongchani/proof-of-delivery
```

검증 결과의 저장소·워크플로·커밋도 승인한 버전과 비교해야 합니다. 이 증명은 **파일과 GitHub 실행의 연결**을 확인하며, 러너가 정직했는지나 AI 판단이 옳은지를 증명하지 않습니다. [GitHub 공식 설명](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)

데모의 기준 지문은 실행 기준, AI 정책, 러너 지문, 암호화 패키지 지문, 키 지문을 포함한 manifest를 고정합니다. 결과 지문에는 실제 검사와 AI 검토 기록을 함께 넣습니다. 계약은 내용 자체를 해석하지 않으며 등록된 서명과 고정 지문을 검사합니다.

소스 키를 결과 제출 전에 공개하여 이의 기간에 열람할 수 있게 합니다. 키 공개는 파일 내용의 품질·전달 가능성·올바른 암호화까지 보장하지 않으며, 고객은 제공된 패키지와 원본을 별도로 확인해야 합니다. 키가 공개되므로 비공개 납품 운영을 위해서는 별도 전달 정책이 필요합니다.
