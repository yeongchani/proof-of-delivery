# 권한과 지급 운영

[README](../README.md)

새 구현은 `AuthorityEscrow`이며 기존 `MilestoneEscrow`와 ABI·서명 형식이 다릅니다. 두 계약 모두 공개 테스트넷 배포를 완료했다고 주장하지 않습니다. 기존 [테스트넷 안내](testnet.md)는 v1 전용입니다.

## 누가 무엇을 결정하나

| 주체                       | 권한                                                     |
| -------------------------- | -------------------------------------------------------- |
| 발주자                     | 고정 조건 제안, 대금 예치, 이의 신청                     |
| 개발자                     | 조건 승인, 이행 보증금 예치, 불통과 이의, 소스 키 인계     |
| 양측 공동                  | 검증자 교체, 기존 계약의 합의 정산과 후속 계약 승인       |
| 양측 각각                  | 결과 제출 전 검증 권한 정지                              |
| 등록 검증자                | 고정 정책과 기준에 대한 결과 서명. 금액·수령인 변경 불가 |
| 계약 배포 때 지정한 중재자 | 이의 사건의 승패 판정. 주소는 불변                       |
| 누구나                     | 조건이 도래한 지급·보관금 지급·기한 환불 호출            |

검증자 교체는 같은 주소·다음 권한 버전에 대한 양측 승인 후 적용합니다. 회수·교체 때마다 버전이 바뀌어 과거 서명은 무효가 됩니다. 통과 결과가 접수된 뒤에는 권한 변경을 동결하고 이의 절차로 처리합니다.

금액·기간·기준·러너 지문·AI 정책은 계약 안에서 덮어쓰지 않습니다. 요구사항을 바꾸려면 새 조건의 후속 계약을 먼저 제안하고, `approveReplacement`로 양측이 같은 후속 계약·기존 대금 정산액·버전에 동의합니다. 승인 완료 시 기존 계약을 닫고 합의한 금액을 개발자에게, 나머지를 발주자에게 지급하며 개발자 보증금은 반환합니다. 후속 계약은 별도로 승인·예치해야 합니다. 제출·분쟁 중 임의 변경은 허용하지 않습니다.

## 시간과 자금

납품 기한이 시작된 계약의 변경 합의는 그 기한 전에 완료해야 합니다. 이전 한쪽 동의만으로 기한 후 환불 권리를 소급해서 없애지 않습니다.

납품 기한은 개발자의 조건 승인 시 시작됩니다. 대금·보증금이 일부만 예치되어도 기한이 지나면 환불할 수 있습니다. 양측 예치가 완료돼야 결과를 접수합니다.

- 정상 지급: 이의 기간 후 키 공개와 함께 대금에서 보관금을 뺀 금액과 개발자 보증금을 지급합니다. 보관금은 지급 시점부터 합의한 기간 후 지급합니다.
- 불통과: 서명된 결과를 기록합니다. 개발자는 이의 보증금을 내고 중재를 요청하거나 보완 후 다시 검수를 받을 수 있습니다. 재검수와 환불이 이의 기회를 없애지 않도록 기한을 검사합니다.
- 개발자 중재 승: 소스 인계가 필요한 경우 인계 대기 상태로 이동합니다. 키 공개와 함께 정상 지급 및 이의 보증금 지급을 처리합니다.
- 고객 중재 승: 대금과 개발자 보증금, 이의 보증금을 고객에게 지급합니다.
- 검증·중재 시간 초과: 대금은 발주자에게, 개발자 보증금은 개발자에게, 이의 보증금은 실제 신청자에게 반환합니다. 무응답을 곧바로 어느 한쪽의 과실로 간주하지 않습니다.
- 키 미제공: 별도 인계 기한 뒤 환불할 수 있습니다. 인계 기한은 정상 검수의 이의 기간 종료 또는 개발자 승소 시점부터, 합의한 이의 기간과 같은 길이로 설정됩니다.

결과 접수 전 키 공개는 거절하고, 접수 후에는 권한 회수를 막습니다. 따라서 계약이 제공하는 인계 경로로 키를 받은 뒤 권한을 회수해 대금을 환불받는 순서는 차단됩니다. 다만 계약 밖에서 소스를 먼저 제공한 경우의 보상, 중재자의 편향, 일한 시간의 가치까지 자동 판정하지는 않습니다.

키는 거래 인수로 전송되므로 대기 중이거나 실패한 거래에서도 노출될 수 있습니다. 특히 인계 기한 직전의 제출은 안전한 비밀 교환을 보장하지 않습니다. 이번 수정은 성공한 거래에서의 인계·지급과 권한 회수 악용을 통제하며, 네트워크 수준의 비밀 전달까지 해결한 것은 아닙니다.

## 지급 호출 프로그램

`keeper`는 명시한 계약 번호만 한 번 확인합니다. 상시 스케줄러를 설치하지 않습니다. 기본값은 조회·시뮬레이션이며 `--send`를 지정할 때만 거래를 보냅니다.

```powershell
npm run build
$env:RPC_URL = '<사용할 RPC>'
$env:CHAIN_ID = '<동일 체인의 ID>'
$env:AUTHORITY_ESCROW_ADDRESS = '<새 AuthorityEscrow 주소>'
npm run keeper -- 1 2
# 가스 비용을 낼 KEEPER_PRIVATE_KEY를 별도 주입한 후에만:
npm run keeper -- 1 2 --send
```

호출자는 지급 대상과 금액을 선택할 수 없습니다. 다른 호출자가 먼저 실행하면 거래가 실패할 수 있으며 무한 재시도하지 않습니다. 상시 호출·가스 잔액·실패 알림 운영은 배포 단계의 과제입니다.

## 증거의 의미

GitHub CI는 `authority-demo-evidence` artifact를 30일 보관합니다. main push에서 테스트가 통과하면 별도 작업이 `authority-demo.json`에 GitHub 출처 증명을 붙입니다. 출처 증명 권한이 있는 작업은 저장소 코드를 checkout하거나 실행하지 않습니다.

다운로드한 파일은 다음 명령으로 확인할 수 있습니다.

```bash
gh attestation verify authority-demo.json -R yeongchani/proof-of-delivery
```

검증 결과의 저장소·워크플로·커밋도 승인한 버전과 비교해야 합니다. 이 증명은 **파일과 GitHub 실행의 연결**을 확인하며, 러너가 정직했는지나 AI 판단이 옳은지를 증명하지 않습니다. [GitHub 공식 설명](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)

데모의 기준 지문은 실행 기준, AI 정책, 러너 지문, 암호화 패키지 지문, 키 지문을 포함한 manifest를 고정합니다. 결과 지문에는 실제 검사와 AI 검토 기록을 함께 넣습니다. 계약은 내용 자체를 해석하지 않으며 등록된 서명과 고정 지문을 검사합니다.

검증자는 소스와 실행 결과를 확인하고, 발주자는 이의 기간에 검수 근거를 확인합니다. 최종 키 공개는 이의 기간 이후 지급과 같은 거래에서 처리합니다. 체인의 키 해시 검사만으로 파일 품질이나 올바른 암호화를 증명할 수는 없습니다. 검증자는 제공된 암호화 패키지가 검수한 소스로 복원되는지도 확인해야 합니다. 공개 키는 파일을 가진 누구나 사용할 수 있으므로 비공개 납품 서비스에는 별도 전달 정책이 필요합니다.
